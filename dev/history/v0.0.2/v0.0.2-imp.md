## 1. 概要

v0.0.2 は **UI 操作性の改善**に集中したバージョン。主なテーマは 4 つ。

1. **画面の縦を稼ぐ** — 設定ダイアログ上半分のアコーディオン折り畳み
2. **キー操作の是正** — グローバルホットキーの変更 UI、JIS 配列でのズームキー修正
3. **右クリックメニューの拡充と削除の安全化** — 非表示 / 開く系コマンド、確認ダイアログ
4. **ドラッグ並べ替えの全面刷新** — 接続先 / テーブル / 列見出し / 列設定表を **同一デザイン**
   （移動元＝破線＋半透明、移動先＝太線バー＋破線囲い）に統一し、列並べ替えの実データ反映まで通す

実装は既存構成を踏襲（フロント: 素の TypeScript `src/main.ts` / バックエンド: Rust + Tauri v2）。

### 2-3. ズームキーの是正（Ctrl+Shift+マイナス / Ctrl+プラス）

> なぜか Ctrl+Shift+マイナスで拡大になるがしなくていい。なぜか Ctrl+プラスで拡大できないので拡大したい。

原因は **JIS 配列と `KeyboardEvent.key` のズレ**。JIS では `+` は Shift+`;`（`code="Semicolon"`）、
`-` キーの Shift は `=`（`code="Minus"`）。WebView2 の既定ズームは `Ctrl+"="` を拡大と解釈するため、
**Ctrl+Shift+マイナス（＝ Ctrl+`=`）で拡大**してしまっていた。

[main.ts:3125-3160](src/main.ts:3125) で `key` ではなく **`code` を主判定**にして解決した。

| 判定 | 条件 |
| :--- | :--- |
| 拡大 | `key === "+"` / `"Add"` / `code === "NumpadAdd"` / **`code === "Semicolon"`（JIS の `+`）** / `code === "Equal" && !shiftKey`（US 配列） |
| 縮小 | 拡大に該当せず、`key === "-"` / `"_"` / `"Subtract"` / `code === "Minus"` / `code === "NumpadSubtract"` |
| リセット | `key === "0"` / `code === "Numpad0"` / `code === "Digit0"` |

いずれも `preventDefault()` を呼ぶため WebView2 の既定ズームは発火しない。結果、
**Ctrl+Shift+マイナスは拡大しなくなり**（縮小として扱う）、**Ctrl+プラス（JIS）で拡大できる**。

### 2-8. 接続先ノードのドラッグ移動・クリック挙動・ドロップ表現

> …展開機能は残したままドラッグで移動／親のシングルクリックもチェック切り替え／移動元・移動先は接続先単位で囲う／境界に太線で「ここに入る」／展開は左端の▼かダブルクリック／ダブルクリック時は1回目のクリックでチェックを切り替えたくない

| 要求 | 実装 |
| :--- | :--- |

### 2-11. 列の入れ替えが実データに反映されない / 列設定が開かない・遅い

> ドラッグしても列の入れ替わりが起こりません。…この列を保有している全てのデータソースの列を入れ替える必要があります。ところが列の設定を開いても「対応するデータソースが見つかりませんでした」となる…そもそも読み込みが遅すぎます。キャッシュしたデータを使ってもっと高速に

3 つの別々の問題だったため、それぞれ対処した。

#### (a) 入れ替えが起こらない → 即時反映＋全データソースへ永続化

列見出しのドロップ時（[main.ts:1052-1120](src/main.ts:1052)）に

1. セッション内の表示順 `gridColumnOrder` を更新 → `rebuildColumns()` + 再描画で**即座に画面へ反映**
2. 続けて、その列を保有する**全データソース**の `config.column_order` を表示名順に並べ替えて保存

の 2 段構えにした。Rust 側 [`make_record`](src-tauri/src/connectors.rs:131) が `column_order` 順に
フィールドを詰め直すため、次回以降の取得結果にも順序が残る（`column_order` に無い列は末尾に追加
されるので、非表示列が欠落することはない）。

#### (b) 「対応するデータソースが見つかりませんでした」

原因は、列設定ダイアログが**接続先へライブ接続してフィールド名を取り直していた**こと。
接続に失敗する / 表示名エイリアスが効いていると実フィールド名と突き合わせできず 0 件になっていた。

**キャッシュ済みの検索結果 `rows` から逆引きする方式**へ変更（[openColumnContextMenu()](src/main.ts:1239)）。
`rows[].fields` のキーは表示名なので、各ソースの `column_aliases` を逆引きして実フィールド名へ戻す。
ライブ接続を一切行わないため、オフラインでも接続エラー中でも列設定が開く。

#### (c) 読み込みが遅すぎる

レビューで、上記 (b) の方式変更後も**アルゴリズム側にボトルネックが残っている**ことが判明したため
本レビューで追加改修した（詳細は §3 バグ 3・4）。

## 3. レビューで発見・修正したバグ

「実装済」項目を通しでレビューし、以下 4 件を修正した。

### バグ 1: 単独の「F」キーがグローバルホットキーとして登録できてしまう

- **箇所**: [main.ts:3038](src/main.ts:3038)（ショートカットキー入力欄の `keydown`）
- **原因**: 修飾キー無しでも許可する条件が `!e.key.startsWith("F")` だった。ファンクションキーを
  意図した判定だが、**英字の「F」も先頭一致してしまう**。
- **影響**: 設定画面で「F」を押すとホットキーが `F` として登録され、**OS 全体で F キーが EveryDB に
  奪われる**（他アプリで F が入力できなくなる）。`Fn` 系の他のキー名も同様に誤判定し得た。
- **修正**: `/^F([1-9]|1[0-9]|2[0-4])$/` で F1〜F24 のみを許可。

### バグ 2: グリッド右クリックの「テーブルを開く」が、開けない種別でも押せる

- **箇所**: [openGridContextMenu()](src/main.ts:650)
- **原因**: サイドバーの右クリックメニューは `TABLE_OPENABLE_TYPES` で出し分けていたのに、
  グリッド側は無条件で有効だった。
- **影響**: CSV / Excel / SQLite など Web ページを持たない種別で押すと、毎回
  「このテーブルは直接開けません」というエラー表示になる（隣の「このページを開く」は
  正しくグレーアウトされるため、挙動が不統一だった）。
- **修正**: 選択行のソース種別を見て `disabled` にする。

### バグ 3: 列設定ダイアログの走査が O(行数 × ソース数) で遅い（要求 (c) の根本原因）

- **箇所**: [openColumnContextMenu()](src/main.ts:1239)
- **原因**: 「ソースごとのループ」の内側で**毎回 `rows` を全件走査**し、さらに 1 フィールドごとに
  `Object.entries(aliases).find(...)` で線形逆引きしていた。加えて `get_source_detail` を
  **ソース数ぶん逐次 `await`** していた。
  行数 10,000 × ソース 20 × 20 列 で数百万回の照合になり、ダイアログが数秒間フリーズする。
- **修正**:
  - `rows` の **1 パス**で `Map<source_id, Set<表示名>>` を作る `buildSourceFieldIndex()` を新設
    （[main.ts:868](src/main.ts:868)）。
  - エイリアス逆引きを `Map` 化する `toRawFieldNames()` を新設（[main.ts:891](src/main.ts:891)）。
  - `get_source_detail` を **`Promise.all` で並列化**（往復 N 回 → 1 バッチ）。
  - 計算量は O(行数 × 列数 + ソース数 × 列数) に低下。取得中は「読み込み中…」を表示。

### バグ 4: 列並べ替え保存が無言でブロックし、完了後に画面が更新されない

- **箇所**: 列見出しドロップ時の一括保存ループ（[main.ts:1073-1120](src/main.ts:1073)）
- **原因**: 保存に使う `update_source` は Rust 側で**当該ソースの再取得（reload）まで行う**。
  対象ソースぶん逐次実行するため、リモート接続（Graph / Google / PostgreSQL 等）が混ざると
  数十秒〜数分かかる。にもかかわらず **UI に一切の進捗表示が無く**、失敗しても
  `console.error` に出るだけだった。さらにバグ 3 と同じ二重走査を含んでいた。
- **修正**:
  - 保存対象を「検索結果に現れたソース」に事前に絞り込み、`(n/N) ソース名` の進捗を
    結果情報バーへ表示。
  - 二重走査を `buildSourceFieldIndex()` / `toRawFieldNames()` に置き換え、
    表示順の照合も `Map` によるランク引きへ変更。
  - 完了後に `refreshSidebar()` を呼び、失敗があれば
    「n/N 件成功、m 件失敗」を表示する（従来は無言で終了し件数表示も消えたままだった）。

### 4-2. 管理トグル

サイドバー見出し行の右端に `#manage-toggle`（[index.html:29](index.html:29)）を設置。
ON でサイドバーに `.manage` クラスが付き、以下が起きる（[main.ts `setManageMode()`](src/main.ts:333)）。

| 挙動 | 内容 |
| :--- | :--- |
| 幅の拡大 | 直前の幅を覚えたうえで **最低 720px** へ拡大。上限は `window.innerWidth - 320`（検索結果側が潰れないように）。OFF で元の幅へ復元。 |
| 幅を永続化しない | 管理モード中はリサイザーで幅を変えても `set_sidebar_width` を呼ばない。次回起動時に広いままになるのを防ぐ（復元用の幅だけ更新する）。 |

管理モードはセッション内の状態で、永続化しない（通常は検索に使う画面のため、
起動時は常に通常モードで開くのが自然と判断）。

### 4-3. 一覧に出す情報

（[styles.css](src/styles.css) の `.m-type / .m-count / .m-last / .m-interval / .m-actions`）。

| 列 | テーブル行 | 接続先行 |
| :--- | :--- | :--- |
| 状態 | 既存の色ドット（成功/失敗/未取得。`title` にエラー全文） | 配下に失敗があれば最終更新を赤字表示 |
| 名前 | テーブル名 | 接続先ラベル + 子テーブル数 |
| 種別 | 種別の閲覧用ラベル（`TYPE_DEFS` から。`title` に内部キー） | 代表種別（`title` に配下テーブル名の一覧） |
| 件数 | そのテーブルのレコード数 | **配下テーブルの全件合計**（太字） |
| 最終更新 | `last_success_at` を `MM-DD HH:mm` へ短縮（`title` に全文・失敗理由） | 配下で最も新しい成功日時 |
| 間隔(分) | 数値入力。変更で即 `set_refresh_interval` | 配下で揃っていれば共通値、揃っていなければ空欄。**入力すると配下全テーブルへ一括設定** |
| 操作 | `⟳` 再読込 / `✎` 編集 / `🗑` 削除（確認ダイアログ付き） | `⟳` 配下を全再読込 / `⚙` 接続設定 / `🗑` 配下を全削除（確認ダイアログ付き） |

### 4-4. 既存操作との干渉を防いだ点

管理モードの行はドラッグ並べ替え・チェック切り替え・ダブルクリック展開と同居するため、
以下を明示的に処理した。

- **管理ボタンのクリックを親行へ伝播させない** — `stopPropagation()` + `preventDefault()`。
  これが無いと、接続先行のボタンを押しただけで（180ms タイマー経由で）チェックが切り替わってしまう。
- **更新間隔の入力欄でドラッグを一時解除** — `draggable="true"` な祖先の内側では入力欄のテキスト選択が
  できないため、`mousedown` で行の `draggable` を false にし、`blur` で戻す。
- **通常モードのホバー再読込ボタン**（`.mini-btn`）は管理モードでは非表示にし、
  操作列の `⟳` に一本化した。

### 4-5. 接続先のテーブル数表示を削除

> データソース画面の接続先にあるテーブル数の表示は削除して

接続先行に出していた子テーブル数のバッジ（`pcount`）を削除した。
数値自体は接続先ラベルのツールチップ（`C:\...\売上管理.xlsx` + 改行 + `(3 テーブル)`）に残してあるので、
必要なときはホバーで確認できる。管理モードの件数列は**配下の全件合計**なので、これとは別物。

## 7. 残件・今後の検討

- v0.0.2-req.md の「未実装」項目は本バージョンで消化済み。
- 管理モードの状態を永続化するか（現在はセッション内のみ）は、実際に使ってみてから判断したい。
- 列見出しドラッグの一括保存は `update_source` が再取得を伴うため、対象が多いと時間がかかる。
  「並び順だけを保存して再取得しない」コマンドを Rust 側に追加すれば大幅に短縮できるが、
  キャッシュ済みレコードの並びは次回更新まで古いままになるため、要相談。
