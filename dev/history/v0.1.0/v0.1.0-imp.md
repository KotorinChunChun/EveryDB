## 1. 実装方針

v0.1.0 は新規コネクタを増やさず、次の順で既存価値を安定させる。

1. CI とトレイ常駐の信頼性
2. 複数語検索の性能と正確性
3. 利用者・開発文書の同期
4. 空状態と既存サンプルによる初回体験
5. 安全なバックアップと再起動復元
6. 配布判断とリリース確認

各フェーズは対象テストと `npm run check:all` が成功した時点で完了とする。コミットログは日本語で残し、1 フェーズまたは1つの独立した不具合修正を1コミットの目安とする。

## 2. 設計上の決定

### 2.1 CI

- 初版は `windows-latest` の単一ジョブとする。
- `npm ci` の後に `npm run check:all` を実行する。
- frontend と Rust を別ジョブにする場合は、`dist/` を artifact で渡す設計を別途行う。
- Playwright の静的ランドマーク検査は導入しない。DOM は既存 Vitest、実操作はリリース時の実機確認で担保する。

### 2.2 トレイとバックグラウンド処理

- ウィンドウの×は「非表示」であり、アプリ終了ではない。
- OAuth 認可待ちの取消とスケジューラ停止を同じ `shutdown_background_tasks` にまとめない。
- スケジューラ停止は `RunEvent::Exit` だけで行う。
- トレイ格納時に必要なら OAuth 取消専用関数だけを呼ぶ。

### 2.3 複数語検索

- 文字数判定は Unicode scalar の `chars().count()` を既存どおり使う。
- 3 文字以上の語は FTS、短い語は LIKE とする。
- FTS 語は引用したフレーズへ変換し、ユーザー入力を FTS 構文として実行しない。
- テストデータには「東京都」「営業部」など本当に3文字以上の語を使う。
- 100,000 行・3語 AND の debug 基準は 500ms を初期目標とし、CI の実測が安定しない場合は測定値と理由を記録して調整する。

### 2.4 空状態

- `samples/customers.csv` を再利用し、`tauri.conf.json` の bundle resources へ追加する。
- ウェルカムモーダルと `onboarding_seen` は作らない。
- ソース 0 件なら常に空状態を表示し、ソース追加後は通常グリッドへ戻す。
- 同名サンプルが存在する場合は重複追加せず、そのソースを選択する。
- `add_source` 後は一覧とステータスを読み直し、取得失敗を利用者へ表示する。

### 2.5 バックアップと復元

- エクスポートは SQLite の整合性を保証できる API を使う。単純な `fs::copy` は使わない。
- 復元コマンドは選択ファイルを app data 配下の一時ファイルへコピーし、SQLite として開いて schema を検証する。
- 復元予約は DB 外の小さなメタファイルに記録し、アプリ再起動後、`cache.db` を開く前に処理する。
- 起動時に現行 DB を日時付きバックアップへ退避し、ステージ済み DB を同一ボリューム内で置換する。
- `cache.db-wal` と `cache.db-shm` が残る場合の削除・復旧を明示的に扱う。
- 新 DB を開けなければ退避ファイルへ戻し、復旧先をログと利用者向けメッセージへ示す。

### 2.6 リリース

- 版番号対象は5ファイルとする。
- コード署名と自動更新を分離する。
- 一般公開なら署名を強く推奨するが、費用・配布範囲はユーザー判断とする。
- LICENSE または利用条件文書の具体的内容は、選択した配布形態に合わせて決める。
