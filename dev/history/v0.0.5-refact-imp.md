### 0-6. コード調査で判明した重点リスク

ここでは断定できる不一致と、実装時に回帰テストで確定させる仮説を分ける。

#### 確認済み

- **生成物の二重管理**: `tsc` が `src/main.js` を生成し、その生成物が Git 管理されている。
  TypeScript と JavaScript の分岐コピーを生み、過去の `IDEAS.md` にも XSS 修正漏れの危険として記録されている。
- **外部参照スキームの不整合**: フロントの `getCellUrl()` は `file:` / `notion:` / `ftp:` /
  `teams:` / `obsidian:` をURLとして認識する一方、Rustの `open_ref` は `http` / `https` /
  `mailto` だけをURLとして扱い、それ以外をローカルパスとして opener に渡す。対応スキームごとの
  契約テストが必要。
- **データソース定義の重複**: 種別IDと能力が、フロントの `TYPE_DEFS`、Rust の
  `build_connector`、秘密フィールド、credential scope、親グルーピング、手順書対応表などに
  分散している。Airtable の共有フィールド漏れ等、過去にこの分散が原因の実装漏れが発生済み。
- **スキーマ移行管理不足**: `CREATE TABLE IF NOT EXISTS` と列追加だけで、schema version、
  段階的 migration、変更前バックアップ、失敗時復旧の仕組みが無い。
- **エラー表現の分散**: フロントに `alert` / `console.error` / DOMへの直接文言設定が多数あり、
  Rust側にも結果を意図的に握りつぶす経路が複数ある。利用者へ出す失敗、statusへ残す失敗、
  無視してよい後始末の失敗を区別する型・規約が無い。

#### 回帰テストを先に作って確認するリスク

- `async` Tauri command 内で同期ネットワーク処理を行い、単一の `Mutex<Connection>` を
  fetch 中も保持する経路がある。描画スレッドは止まらなくても、検索・一覧・他の更新が長時間
  DB lock 待ちになる可能性がある。fetch とDB commitを分離して計測する。
- 各追加・更新・一括リロードで FTS `optimize` を発行するため、頻度によっては高速化より
  書き込み待ちが増える可能性がある。バッチ単位の1回へ集約する前後で測定する。
- Box OAuth の `state` が時刻+PIDで生成されており、OAuthのCSRF nonceとして予測困難性が弱い。
  暗号学的乱数へ変更し、state不一致・取消・タイムアウトを統合テストする。
- `open_ref` の禁止拡張子方式は防御として有効だが、URL・UNC・カスタムスキーム・拡張子なしの
  境界がテスト不足。許可方式と拒否方式を再検討する。
- ignored live test の一部は長期間未実施。特に Intune、Box CCG、PostgreSQL/MySQL TLS、
  Access ODBC は「実装済み」と「実環境で確認済み」を文書上で分離する必要がある。

## 1. リファクタリング原則

1. **挙動をテストで固定してから移動する。** 機能追加と構造変更を同じコミットへ混ぜない。
2. **既存データを捨てない。** DB・credential参照・localStorageの旧形式から自動移行する。
3. **1コミット1責務。** format、テスト基盤、モジュール抽出、バグ修正、文書を分離する。
4. **依存方向を一方向にする。** UI → application/service → IPC/repository → connector/infrastructure。
5. **種別ID・能力の重複を検査可能にする。** 完全な動的フォーム化は行わず、共通manifestと
   coverage testで登録漏れを止める。
6. **秘密情報をフロントへ常駐させない。** 現在のDPAPI・credential参照・Windows Helloを維持し、
   一時的な復号値の生存範囲を狭める。
7. **未検証を実装済みと混同しない。** 自動、モック、ライブ、手動の検証レベルを文書へ明示する。
8. **機械的な行数削減を目的にしない。** 境界、テスト可能性、変更影響の限定を成果とする。

## 2. 目標アーキテクチャ

### 2-1. フロントエンド（素の TypeScript を維持）

予定構成。実装中に責務境界が不自然と判明した場合は、理由を §8 に記録して調整する。

```text
src/
  main.ts                       # bootstrapのみ
  app/
    bootstrap.ts                # 初期化順序・イベント購読
    state.ts                    # アプリ状態と更新API
    ipc.ts                      # 型付き invoke wrapper
    dom.ts                      # DOM取得・共通生成ヘルパー
  shared/
    types.ts
    errors.ts
    storage.ts
    clipboard.ts
  source-types/
    registry.ts                 # 設定フォーム定義。共通manifestとの対応を検査
    url-parsers.ts
    parent-groups.ts
  features/
    sources/                    # サイドバー、管理モード、並べ替え、context menu
    search/                     # 検索要求、履歴、プリセット
    grid/                       # 列・行描画、仮想スクロール、選択、sort/resize
    source-editor/              # 追加・編集、列役割、親接続設定
    pickers/                    # Excel/Notion/Airtable/SharePoint/browser
    credentials/                # token picker/manager、Windows Hello
    export/                     # TSV/CSV/JSON
    guides/                     # Markdown表示
    settings/                   # theme/zoom/hotkey/autostart/sidebar
  styles/
    tokens.css
    themes.css
    layout.css
    components.css
    dialogs.css
```

設計上の要点:

- グローバル可変状態を `AppState` と明示的な更新関数へ集約し、機能モジュールが互いの内部変数を
  直接変更しないようにする。
- `invoke("文字列")` を各所へ散らさず、引数・返り値を型付けした `ipc.ts` に集約する。
- DOMイベントは feature 単位で `mount` / `dispose` または一度だけの初期化関数を持たせ、
  handlerの重複登録を防ぐ。
- テスト可能な純粋関数（URL解析、sort、export、列選択、state復元）とDOM操作を分離する。
- `index.html` は当初DOM IDを維持したままにし、テストが揃ってから重複dialogだけを段階的に整理する。

### 2-2. Rust / Tauri

```text
src-tauri/src/
  lib.rs                        # Tauri組み立てのみ
  app_state.rs
  commands/
    mod.rs
    sources.rs
    search.rs
    browse.rs
    credentials.rs
    settings.rs
    opener.rs
  db/
    mod.rs
    migrations.rs
    source_repository.rs
    record_repository.rs
    search_repository.rs
    metadata_repository.rs
  connectors/
    mod.rs                      # Connector trait・factory・registry
    common.rs
    local/                      # csv/sqlite/excel/access/folder/ime/browser
    databases/                  # postgres/mysql
    microsoft/                  # Graph/SharePoint/OneDrive等
    cloud/                      # notion/airtable/google/box/ical
    public_data/                # postal/corporate/pokeapi/web_page
  services/
    refresh.rs
    credentials.rs
    source_config.rs
  security/
    dpapi.rs
    windows_hello.rs
    oauth.rs
```

設計上の要点:

- connector fetch はDB lock外で実行する。短時間の「設定取得」「結果commit」「status更新」だけで
  connectionを保持する。
- refresh結果を `success / failed / cancelled` と件数付きで返し、複数件更新では部分失敗を
  UIへ伝えられるようにする。
- FTS最適化は一件ごとではなくバッチの最後へ集約し、失敗はログ/status方針に従う。
- DBへ `schema_version` を導入し、各migrationを冪等・トランザクション化する。
- connector typeは共通manifestでID・表示名・分類・能力を定義し、Rust factoryと
  TypeScriptフォーム定義の全件対応をテストする。

### 2-3. 共通データソースmanifest

`shared/source-types.json`（仮称）に、少なくとも次を持つ。

- 安定した type ID
- 利用者向け名称とカテゴリ
- 親グループ種別
- credential scope
- browse / open / live-test / guide の対応能力
- app内手順書ファイル名

入力フィールドの細かなDOM構築やコネクタ実装自体は各言語側に残す。テストで
「manifestにあるのにfactoryが無い」「秘密フィールドがあるのにscopeが無い」等を失敗させる。

## 5. バグ修正・セキュリティ監査方針

### 5-1. 計画時点で修正対象に入れるもの

1. README・ガイド・manifest versionの不一致。
2. `src/main.js` の追跡とTypeScript emit設定。
3. `open_ref` とフロントの対応スキーム不一致。
4. Box OAuth stateの予測困難性。
5. DB lockを保持したまま行う外部fetch。
6. refresh/optimize/emit等の握りつぶされたエラーの分類と通知。
7. source type registryの分散による登録漏れ。
8. schema migration/version/backup不足。
9. Rust format/Clippyエラー。

### 5-2. 監査するもの

- DPAPI暗号文、`cred:<id>`、refresh tokenがログ・エラー・フロントstateへ漏れないこと。
- Windows Helloの10分キャッシュと利用不能時fallbackが文書どおりであること。
- OAuth callbackがloopback以外へbindせず、stateを必須検証すること。
- Web取込・政府データ・各APIのtimeout、レスポンス上限、ページング上限。
- SQL identifier検証、LIKE/FTS query生成、ODBC/PostgreSQL/MySQL TLS設定。

## 8. 実装で判明した追加対応

### 8-1. 保存済みcredentialの未保存ブラウズ時に秘密値がIPCを通過する

**発見内容:** `credential_secret_value` は、コピー操作では Windows Hello 確認後に呼ばれる。一方、未保存の
Notion/Airtable/SharePoint 接続確認では、保存済みcredentialを選択した場合に同コマンドを直接呼び、
復号済みtoken/client secretをフロントエンドへ返している。

**仕様との差異:** 「秘密情報をフロントへ常駐させない」「一時的な復号値の生存範囲を狭める」という本計画の
原則に対し、IPC経由でJavaScript変数へ渡る経路がある。外部APIへの確認機能は維持されるが、コピー操作と
同じ本人確認にもなっていない。

**提案（要ユーザー判断）:** 推奨は、credential ID と必要な非秘密設定だけをRustへ渡す専用browse commandへ
置換し、Rust側でcredentialを解決して外部APIを実行する方式である。これによりフロントへ平文を返さず、
未保存の接続確認も維持できる。代替として、現行経路を維持し、Windows Hello確認を必須化したうえで
「確認中だけ一時的にフロントへ渡る」例外をセキュリティ文書へ明記する案がある。

現時点では計画外対応なし。計画から逸脱した対応は、理由・影響・検証結果とともにここへ追記する。
