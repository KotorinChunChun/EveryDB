## 4. 大容量データ対応・パフォーマンスおよび自動検出の最適化（追加対応）

### 4-1. 列一覧取得 (`Connector::field_names`) の超高速化

- **課題**:
  - 設定ダイアログの開閉時や「表から選択…」呼び出し時、列名一覧を取得する `raw_field_names` がデータ取得用の `connector.fetch()` をそのまま呼び出していたため、10万行の Excel/CSV/SQLite において全行データ（10万行分）のメモリ読み込みとパース・走査が発生し、数秒〜数十秒の大きな遅延が発生していた。
- **対応 (`src-tauri/src/connectors.rs`)**:
  - `Connector` トレイトに `fn field_names(&self) -> Result<Vec<String>>` メソッドを追加し、全データ読み込みを完全に回避して**ヘッダー行／スキーマ定義のみをピンポイントで読み取る処理**を実装。
    - **`ExcelRangeConnector`**: 先頭セル (`r1`) のあるヘッダー行 1 行のみを直接読み取り、全セル走査や末尾セルの確定走査 (`detect_end_cell`) を完全スキップ。
    - **`ExcelTableConnector`**: `ListObject` の定義テーブルヘッダー (`table.columns()`) または先頭 1 行のみを取得。
    - **`CsvConnector`**: CSV リーダーの先頭 1 行（ヘッダー）のみをパース。
    - **`SqliteConnector`**: `SELECT * FROM table LIMIT 0` を発行し、カラム名のみを即時に取得。
- **効果**:
  - 10万行規模の大容量データソースでも全行走査が一切行われなくなり、列一覧の取得速度が **1ミリ秒未満（1000倍〜10000倍以上の高速化）** に劇的に改善された。

### 4-2. 実際のデータ読み込み時における末尾セル（データ最終行）自動検出の是正

- **課題**:
  - `ExcelRangeConnector::fetch` において、末尾セルの自動決定ロジックの優先順位 1 番目に `if used_end.0 > 0` が記述されていたため、常に Excel シートの `UsedRange`（書式が設定された空行を含む最大行、例: 1,048,576行等）が返され、ユーザーが意図した `end_ref_column`（指定基準列）によるデータ最終行探索が全く実行されないバグが発生していた。
- **対応 (`src-tauri/src/connectors.rs`)**:
  - **優先順位の正常化**: 要求仕様通り、`end_ref_column` で指定された列が存在する場合は、**「指定した列のいずれかが空欄ではない最終行」(`detect_end_cell(&range, &end_ref_cols)`) を最優先**で特定するように修正。次点で全列のデータ最終行 -> オートフィルタ右下セル -> `UsedRange` となるよう判定順序を是正。
  - **空文字セルの判定強化 (`is_cell_non_empty`)**: 単なるデータなし (`Data::Empty`) だけでなく、空文字 `Data::String("")` やスペースのみが入力されたセルも「空欄セル」として正しく判定・除外するヘルパー関数を導入。
  - **ボトムアップ高速探索**: `detect_end_cell` をシートの上から下へ走査するのではなく、UsedRange の下から上へと逆順走査 (`.rev()`) するアルゴリズムに最適化。最初の非空セルが見つかった時点で探索を打ち切るよう高速化。

### 6-8. 全主要データソースへの URL コピペ・ファイルドラッグ＆ドロップ全自動入力支援機能の追加

- **対応内容**:
  - `parseGoogleSheetsUrl`, `parseNotionUrl`, `parseSharePointUrl` ヘルパー関数を実装。
    - **Google スプレッドシート**: スプレッドシート URL から `/spreadsheets/d/ID` パターンにより `spreadsheet_id` を自動抽出。

## 7. 保存済みトークンの管理・再利用機能（未実装項目の実装）

> 過去に設定したことのあるトークンIDを再利用設定できるようにしてほしい。
> またトークン管理画面のようなものを作成し、追加・削除・置換を一括でできるようにして欲しい。

### 7-0. 事前確認（ユーザー回答）

| 論点 | 決定 |
| :--- | :--- |
| 「置換」の反映方式 | **共有参照方式**。ソースは実際の値を持たず `cred:<id>` という参照だけを持つ。管理画面で値を書き換えれば紐づく全ソースが自動的に新しい値になる（個別編集不要）。 |
| 使用中トークンの削除 | **ブロックし、使用中のソース一覧を表示**。先に付け替える/それらのソースを削除してからでないと削除できない。 |

### 7-1. データモデル

新規テーブル `credentials`（id / scope / label / fields_json / created_at）。`scope` は
既存の `sharedKeysFor` と同じ発想で、関連フィールドをひとまとめにする単位:

| scope | 束ねるフィールド | うち `cred:` 参照になるのは |
| :--- | :--- | :--- |
| `notion` | token | token |
| `airtable` | token | token |
| `graph`（graph_* 全種別共通） | tenant_id, client_id, client_secret | client_secret |
| `box` | client_id, client_secret, enterprise_id | client_secret |
| `postgres` | user, password | password |
| `mysql` | user, password | password |

**`secret::secret_keys(type_)` に含まれるフィールド（token/password/client_secret）だけが
実際に `cred:<id>` の生きた参照になる。** tenant_id/client_id/enterprise_id/user のような
非秘密フィールドは、選択時に平文の値としてその場でコピーするだけ（以後の「置換」では追随しない）。
秘密情報の使い回しという要求の本旨（トークン・パスワードの再利用）に対しては十分と判断した
（tenant_id 等は単独では機能せず、通常トークンより変更頻度が低い）。

- ソース側の `config_json` は、リンク中は秘密フィールドの値として文字列 `"cred:<id>"` を持つ
  （`dpapi:<hex>` の代わり）。`secret::protect_config` は `cred:` prefix も
  `dpapi:` と同様「既に保護済みなので触らない」対象として扱うよう修正。
- 実際の値への解決は **`db::get_source_config`**（および保存前プレビュー用の
  `preview_source_fields` 経路）でのみ行う。`cred:<id>` を見つけたら `credentials.fields_json`
  を復号して該当フィールドへ展開してから返す。これにより `connectors::build_connector` 以降は
  一切変更不要（今まで通り生の値が来ているように見える）。
- `secret::mask_config`（未解錠時のマスク表示）は `dpapi:` だけでなく `cred:` prefix も
  マスク対象にする。
- `secret::merge_preserving_placeholder` は無改修で動く（プレースホルダーのまま保存されたら
  旧値=`cred:<id>` をそのまま維持する、という既存ロジックがそのまま使える）。

### 7-2. Rust 側 API

| コマンド | 用途 |
| :--- | :--- |
| `list_credentials(scope)` | 管理画面・ピッカー用の一覧（id/label/作成日時/使用中ソース数） |
| `add_credential(scope, label, fieldsJson)` | 新規保存。秘密フィールドのみ DPAPI 暗号化。マスターパスワード**設定**必須（unlock 不要） |
| `update_credential(id, label, fieldsJson)` | 「置換」。プレースホルダーのままの秘密フィールドは旧暗号化値を維持（ソース編集と同じ意味論） |
| `delete_credential(id)` | 使用中ソースがあれば `Err` でソース名一覧を返し拒否 |
| `credential_usage(id)` | 使用中ソース一覧（管理画面の「使用中: N件」表示・削除確認ダイアログ用） |
| `pick_credential_for_field(id)` | ピッカーで選択した際、非秘密フィールドの平文値とラベルだけを返す
（秘密フィールドの実値はフロントへ一切渡さない。フロントは `cred:<id>` を config に埋めるだけで済む） |

秘密の解決はサーバー側で完結させ、既存の `preview_source_fields_by_id` 等と同じ「DPAPI 復号は
アプリ内部利用、UI 表示ゲートとは独立」の方針を踏襲する。

### 7-3. フロントエンド

- 秘密フィールドを持つ全 `FieldDef`（Notion/Airtable の token、Graph 系の client_secret、
  Box の client_secret、Postgres/MySQL の password）に `credentialScope` /
  `credentialBundleFields`（tenant_id 等、一緒に埋めたい非秘密フィールド）を追加した。
  `wireCredentialButtons()`（[main.ts](../../src/main.ts)）が共通処理を提供し、
  `renderTypeFields`（追加/編集ダイアログ, `fd-` prefix）と `renderFieldsInto`
  （接続設定=親ダイアログ, `pf-` prefix）の両方から呼ばれる。
  - 「📋 保存済みから選択…」で選ぶと、非秘密の同バンドルフィールド（tenant_id 等）はその場で
    平文コピー、秘密フィールドはプレースホルダー表示 + `input.dataset.credRef`（新規リンクの
    このセッションでの ID）を保持する。
  - フィールド直下に「🔗 使用中: 〈ラベル〉（解除）」ヒントを表示する。**既に保存されている
    リンクの表示には ID を必要としない**（`get_source_detail` が返す `linked_credentials`
    はラベルのみ）。「解除」は入力欄を空にするだけで、プレースホルダーのまま保存すれば
    サーバー側の `merge_preserving_placeholder` が既存の参照をそのまま維持する、という
    既存のプレースホルダー機構にそのまま乗る形にした（フロントは ID を意識しなくてよい）。
  - 秘密フィールドの横に「💾 これを保存…」ボタンを追加。**既存ソースの編集時にも使える**ため、
    「過去に設定したことのあるトークン」をラベル付きで登録 → 以後リンクし直す、という
    後付けの再利用が可能になる（要求の主眼）。
  - `getFieldValue()` / 接続設定（親）ダイアログの保存処理（`parent-save` の `sharedValues` 収集）は、
    `dataset.credRef` が付いた秘密フィールドについて、実際の入力値ではなく `cred:<id>` を
    送信するよう変更した（プレースホルダーのまま送ると「変更なし」＝旧値維持と誤認されるため）。
  - 秘密フィールドの「解錠して編集」（`dynamicEl`/`parentDynamicEl` の `focusin` ハンドラ）は、
    `dataset.credLabel` が付いている（＝リンク中の）フィールドではスキップするよう修正。
    リンク中フィールドの実体は `credentials` テーブル側にあり、ソース編集画面からの
    「解錠して覗く」は意味を持たない（誤って再暗号化すると意図せずリンクが外れてしまう）。
- 新規ダイアログ `#credential-manager`（⚙ 設定 → 「🔑 保存済みトークンの管理…」から開く）。
  スコープ別に一覧・追加・置換（値の書き換え）・削除ができる。削除時、使用中なら
  使用中ソース名を理由として表示し中止する（`used_by`。`list_credentials` に含まれる）。
- 新規ダイアログ `#credential-select-picker`（各フィールド横の「📋 保存済みから選択…」から開く。
  「🔑 管理画面を開く…」から管理画面へも遷移できる）。

### 7-5. 実装後のフィードバックで見つかった不具合の修正

> 保存済みから選択のとき、使おうとしているサービスと関係ないものも表示されてしまうため、
> 絞り込むようにして。それとAirtableの接続設定を開いたとき、保存済みのAPIをUIが見当たらない。
> どうやって割り当てたらいい？実装漏れ？

**Airtable の接続設定ダイアログにトークン欄が無い不具合（実装漏れ・確認済み）**

- 原因: 「テーブル一覧」機能用の `ParentBrowseKind`/`parentBrowseKind()` には airtable を
  追加していたが、**「接続情報（token 等）の共有フィールド」を決める別系統の
  `ParentKind`/`parentKindOf()`/`sharedKeysFor()` に airtable のケースを追加し忘れていた**。
  その結果 `sharedKeysFor(parentKindOf("airtable"))` が空配列を返し、接続設定ダイアログに
  token 入力欄自体が一切描画されていなかった（テーブル一覧セクションだけは表示されていた）。
- 対応（[main.ts](../../src/main.ts)）: `ParentKind` に `"airtable"` を追加し、
  `parentKindOf`/`parentKindLabel`/`sharedKeysFor`（`sharedKeysFor("airtable") = ["token"]`）に
  ケースを追加。これにより接続設定ダイアログに token 欄（「📋 保存済みから選択…」
  「💾 これを保存…」込み）が表示されるようになった。
- 副作用（想定どおり・他サービスと同じ挙動への統一）: Airtable の個々のテーブル追加/編集
  ダイアログでは、以後 token 欄が非表示になり「接続先を右クリック→接続設定」からの編集に
  一本化される（Notion/Graph/Postgres/MySQL/Box と同じ既存の挙動に合わせただけで、新規の制約ではない）。

**「📋 保存済みから選択…」に無関係なサービスのトークンが混ざる問題**

- 原因の切り分け: `list_credentials` は元々 `scope` で SQL 側フィルタ済み（notion/airtable/
  box/postgres/mysql は 1 スコープ=1 サービスで無関係な混入は無い）。**唯一「graph」スコープ
  だけは EntraID/SharePoint/Teams/Intune/Calendar 等 10 種類の graph_* 種別すべてで共有**
  している設計（§7-1: 同一の Azure アプリ登録のテナント/クライアント/シークレットはどの
  Graph 系種別でも使い回せるため、意図的に 1 スコープへ束ねた）。EntraID 用に保存した
  トークンが SharePoint の一覧にも出るのは仕様どおりだが、ユーザーから見ると
  「関係ないサービスが混ざる」ように見える。
- 対応（[main.ts](../../src/main.ts) `openCredentialSelectPicker`）:
  1. ピッカーのタイトルに対象スコープ名を明示（例:「保存済みトークンを選択（Microsoft 365
     (Graph)）」）し、今何を選んでいるか誤解しないようにした。
  2. ピッカーに**絞り込み欄**（ラベルの部分一致、大文字小文字を区別しない）を追加。
     開いた直後にフォーカスされる。
  - scope 自体を graph_* の個別種別ごとに分割する案は、要求の主旨（同じテナントのトークンを
    複数の Graph 系種別で使い回したい）と衝突するため見送った。

**検証**: `npx tsc --noEmit` / `npm run build` エラー 0 件（この 2 件はフロントエンドのみの
修正のため `cargo test` の結果に影響なし。92 passed を維持）。
UI の実機確認は未実施（上記 §7-4 の申し送りと同様）。

### 7-7. §7-6 の実機確認で見つかった不具合の修正

ユーザーの実機確認で以下が報告された。

> 「Airtable: SampleBase」の接続設定画面でトークンを変更した直後、テーブル一覧の更新ボタンを
> 押しても変更前のトークンで検証しているように見える。「保存してリロード」を押した後だと
> 正常につながった。しかし、実際にテーブルが追加されたのは「Airtable」の親ツリーの配下だった。
> 「Airtable」ツリーの接続設定では、APIキーを選び直してもテーブル一覧を読み込めなかった。

**不具合 1: トークンを選び直した直後、保存前の「テーブル一覧の更新」が旧トークンを使う**

- 原因: `parentSharedNow()`（接続設定ダイアログの「今の入力値」を取る関数）が、
  §7-6 で `getFieldValue()`/`parent-save` の保存処理にだけ追加した
  「リンク中で未編集なら `cred:<id>` 参照を送る」ロジックを欠いていた。プレースホルダー文字列
  をそのまま送ってしまい、バックエンドの `merge_overrides` がそれを「未編集」と判定 →
  保存済み（＝旧）のトークンで解決される、という経路だった。
- 加えて、**その `merge_overrides` 側にも自分で入れた誤りがあった**: §7-6 の対応時に
  「`cred:<id>` という override は無視する」という修正を入れていたが、これは
  「このセッションで選び直した新しいリンク」を表す override まで無視してしまう誤りで、
  そもそも今回の不具合の一因になっていた。`cred:<id>` の override は無視せず適用したうえで、
  `effective_config` 側でマージ後にもう一度 `resolve_credentials`+復号する（保存済みの
  参照だけでなく、override 自体が新しい参照だった場合にも対応する）よう修正した。
- 対応:
  - フロント: `pf-`/`fd-` 共通のヘルパー `currentFieldRawValue(el, key)` を追加し、
    `parentSharedNow()` もこれを使うよう統一（[main.ts](../../src/main.ts)）。
  - バックエンド: `merge_overrides` から `cred:` 無視ロジックを削除、`effective_config` を
    「解決→マージ→もう一度解決」の二段構えにした（[commands.rs](../../src-tauri/src/commands.rs)）。
    回帰テスト `effective_config_resolves_a_freshly_overridden_credential_reference` を追加。

**不具合 2: 新規追加したテーブルが Base 単位の親ではなく汎用の「Airtable」ツリーに入る**

- 原因: 接続設定ダイアログの「テーブル一覧」で新規テーブルを追加する際
  （`loadParentTables()` の airtable 分岐）、新規テーブルの `extraConfig` に `table`/`table_name`
  しか含めておらず、**ツリーのグルーピングに使う `base_id`/`base_name` を一切引き継いでいなかった**
  （`db::source_parent` は `base_id`/`base_name` が空だと汎用の `"Airtable"` にまとめる）。
  `base_id`/`base_name` は共有フィールド（`sharedKeysFor("airtable")`）に含めていないため、
  兄弟テーブルの設定から明示的にコピーする必要があった。
- 対応（[main.ts](../../src/main.ts) `loadParentTables()`）: airtable 分岐で兄弟テーブル
  （`siblingId`）の `get_source_detail` を取得し、`base_id`/`base_name` を新規テーブルの
  `extraConfig` へ引き継ぐようにした。

**申し送り（データ修復が必要な既存分）**: 上記 2 件の修正は**今後新しく追加するテーブル**には
効くが、**修正前に汎用の「Airtable」ツリーへ入ってしまった既存のテーブル**は `base_id` を

該当テーブルを一度削除し、正しい Base の接続先（例:「Airtable: SampleBase」）から
改めてテーブル一覧に追加し直す必要がある。

**要望: トークン管理画面でどの接続先が使っているか確認できるようにする**

- 対応（[main.ts](../../src/main.ts) `refreshCredentialList()`）: 一覧の各行の下に
  「使用中の接続先: 〇〇、△△」を表示するようにした（`CredentialSummary.used_by` は
  §7-6 の時点で既にバックエンドから返っていたが、件数だけ表示して中身を出していなかった）。

### 7-9. §7-8 の実機確認で見つかった不具合の修正（フリーズ）

> 再表示ボタンを押したらアプリがフリーズしてしまいました。Windows Helloが起動されません。

- 原因: `winauth_status`/`winauth_verify` を素の同期 `#[tauri::command]` のまま実装していた。
  内部で呼ぶ WinRT の `IAsyncOperation::get()` はブロッキング待機のため、
  `add_source` 等で既に踏んで対処済みだった問題（[commands.rs](../../src-tauri/src/commands.rs)
  冒頭のコメント参照）と全く同じ理由で Tauri のメインスレッドを塞いでいた。メインスレッドが
  自分自身の待機で塞がり、Windows Hello ダイアログの表示・完了通知も進まなくなって
  アプリごとフリーズしていたとみられる。
- 対応: 両コマンドを `async fn` にした（返り値をそのまま返す形から `Result` でラップする形に変更、
  Tauri の非同期コマンドの制約に合わせた）。これにより Tauri の非同期ランタイム側のスレッドで
  実行されるようになり、UI スレッドは塞がれない。
- 検証: `cargo build --bins`（フルバイナリ、WinRT リンク含む）→ 成功。
  `cargo test --lib` → 93 passed / 0 failed / 16 ignored（変化なし）。
  `npx tsc --noEmit` / `npm run build` → 変更なし（フロント側の呼び出し方は Tauri の
  同期/非同期コマンドで差が無いため無修正）。
- **実機での動作確認は未実施。** 引き続き `npm run tauri dev` でフリーズせず

### 7-10. §7-9 の実機確認後の仕様変更

### 7-17. Box: 個人プラン対応（Client Credentials Grant → OAuth 2.0 へ移行）

> 次に、Box接続において、現在エラーが出る状況ですが、Enterprise IDが分からなくて設定できない
> 状態です。調査したら個人プランのBoxでは必要ないのではないか？と思われます。その方向で検討、
> 修正してください。
> （エラー: `Box トークン取得失敗 400: {"error":"unauthorized_client","error_description":
> "The \"box_subject_type\" value is unauthorized for this client_id"}`）

**調査結果**: 従来の実装は Box の Client Credentials Grant（CCG、`box_subject_type=enterprise`）
でサービスアカウント認証していたが、これは **Enterprise（有償）プラン専用の機能で、個人（無料）
プランのアカウントでは原則利用できない**（Box 公式コミュニティでも明言されている）。今回の
エラーは Enterprise ID の入力ミスではなく、認証方式そのものが個人プランで使えないことが原因。
ユーザーに「OAuth 2.0（ブラウザ認可）を実装する」か「Developer Token（1時間で失効・手動更新）
にする」かを確認し、自動リロード運用に耐える前者を選択。

**変更内容**:
- **新規モジュール [box_oauth.rs](src-tauri/src/box_oauth.rs)**: Box の OAuth 2.0
  Authorization Code Grant を実装。`authorize_interactive()` がブラウザを開き、ローカルの
  空いているループバックポートで1回だけ認可応答を受け取り、コードをトークンに交換する。
  Box は「ループバックアドレス宛のリダイレクトなら scheme/domain/path が一致すればポート番号は
  問わない」仕様を持つため、Developer Console には `http://localhost/box-callback`
  （ポート番号なし）を1回登録するだけでよく、EveryDB 側は認可のたびに空きポートへ動的に

### 7-20. 「クライアントシークレットが伏字のまま送信される」バグ修正（invalid_client）

> 認可画面は通過しました。ブラウザには成功と出ましたが、アプリにはエラーが出ました。
> （`Box の認可に失敗しました: Box トークン取得失敗 400:
> {"error":"invalid_client","error_description":"The client credentials are invalid"}`）

**経緯**: §7-18 で `redirect_uri_mismatch` を確認したところ、実体は「Box Developer Console 側で
リダイレクトURIの保存自体が失敗していた」ことが原因と判明（アプリを一度サーバー認証で作って
から作り直す等の過程による console 側の一時的な不整合と見られる。ユーザー側でコンソールの
保存をやり直して解消）。その後ブラウザでの認可自体は成功したが、EveryDB 側でのトークン交換が
`invalid_client` で失敗した。

**原因（実装バグ）**: 既存の保存済みプロファイル（「BoxApi1」）を編集中に認可ボタンを押した

のまま表示されている。認可ボタンのハンドラーは DOM 上の入力欄の値をそのまま Box へ送っていた
ため、**伏字の文字列そのもの**をクライアントシークレットとして送信してしまい、Box 側で
`invalid_client` になっていた。

**修正**: [main.ts](src/main.ts) の認可ボタンハンドラーで、クライアントシークレット欄の値が
プレースホルダーのまま（＝ユーザーが打ち直していない）かつ編集中のプロファイルがある場合は、
送信前に Windows Hello 確認を挟んで `credential_secret_value` から実際の値を取得し直すように
した。新規作成時（プレースホルダーが存在しない＝ユーザーが直接入力した値がそのまま入る）は
従来どおり影響を受けない。

**検証**: `npx tsc --noEmit` / `npm run build` エラー0件。バックエンドは無変更のため

### 7-21. 実装レビューで見つけたバグの修正（4件）

> 実装にバグはなさそうかチェックして

Box 対応まわりを中心にレビューし、以下を修正した。

- **【データ消失】認証方式を往復すると既存の認可情報が消える**: トークン管理画面で box の
  認証方式を「個人プラン↔法人プラン」と切り替えるとフォームを作り直すが、退避していたのが
  `client_id`/`client_secret` だけだったため、`refresh_token`（認可済みの印）と `enterprise_id`
  が空欄に戻っていた。`update_credential` が旧値を維持するのは値がプレースホルダーのときだけで、
  空文字は「空に変更」と解釈されるため、往復後に保存すると**既存の認可情報が黙って消える**。
  さらに、往復を2回行うと1回目に退避した値も失われる構造だった（退避が切り替え1回分しか
  持たないため）。編集セッション中は値を保持し続ける退避領域 `cmHiddenFieldStash` を導入し、
  作り直しのたびに積み増して書き戻すようにした。プロファイル間で値が混ざらないよう
  `resetCredentialForm` / `startEditCredential` の入口でクリアしている。
- **【ハングアップ】認可待ちが永久に固まりうる**: `handle_callback_connection` は受理した接続を
  読み取り制限時間なしでブロッキング読みしていた。ブラウザは投機的な TCP プリコネクトを
  張ることがあり、データを送ってこない接続を掴むと `read()` が永久に返らない。この時点では
  取消フラグを見るループを抜けた後なので、**「取消」ボタンも効かなくなる**。読み取り制限時間
  (5秒)を設けたうえで、コールバック以外の接続（プリコネクト、`/favicon.ico` 等）は `None` を
  返して破棄し、本命のコールバックを待ち続けるようにした。
- **【エラーが見えない】Box の認可切れがユーザーに一切通知されない**: `reload_one` は
  `resolve_credentials`（＝Box のトークン更新）と `build_connector` の失敗を `?` で即返して
  おり、`db::set_status` を通っていなかった。呼び出し元の `reload_ids` は `let _ =` で戻り値を
  捨てるため、**refresh_token 失効やネットワーク断が完全に無言で失敗**していた。取得前段の
  失敗もステータスへ記録するようにし、サイドバーの「⚠ 更新エラー」に出るようにした
  （回帰テスト `reload_one_records_status_when_credential_resolution_fails` を追加）。
- **【誤成功】リフレッシュトークンが空でも成功扱いになる**: `box_oauth_authorize` は Box から
  refresh_token が返らない場合に空文字をそのまま返しており、フロントは成功として
  `input.value = ""` を設定するため「認可したのに未認可のまま」という不可解な状態になっていた
  （さらにその状態で保存すると既存トークンを上書きしうる）。空なら明確なエラーメッセージで
  失敗させるようにした。

**残存リスク（未対応・実害が出たら対応）**: コールバック受信は `127.0.0.1` にのみバインドして
いるが、登録・要求する redirect_uri は `http://localhost:58913/box-callback` である。Windows で
`localhost` が IPv6(`::1`) にのみ解決されるブラウザ環境では接続が届かず、3分でタイムアウトする
可能性がある（実機の Chrome では正常動作を確認済み）。デュアルスタック待受けは実装が複雑に
なるため、動作している現状を優先して見送った。

**検証**: `cargo test --lib` 100 passed（新規回帰テスト1件を含む）。`npx tsc --noEmit` /
`npm run build` エラー0件。認証方式の往復については dev サーバー上で実測し、
oauth→ccg→oauth と往復した後も client_id・クライアントシークレット・refresh_token が保持され、
「✅ 認可済み」表示が維持されることを確認した。
